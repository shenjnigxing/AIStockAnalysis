## 三、独立用户批判
- **优点**：系统明确告诉用户“0 个已记录版本”“0 个价格观察点”“PIT 未通过”“真实推荐禁止”，不会偷偷显示模拟收益；版本有可查询来源、指纹和修订历史。
- **缺陷 P0**：`provider_recorded` 并非当时已公开的 PIT；投资者现在仍然得不到任何一只真正可核验的真实推荐。需要公告时点、复权事件、交易日历、可成交性和样本外验证。
- **缺陷 P0**：应用仍使用旧 `Base.metadata.create_all` 启动数据库；生产迁移必须由 DBA 运行并核验独立 SQL、触发器和最小权限。此脚本未经 PostgreSQL CI 验证。不能直接拿开发版 DB 更新生产。
- **缺陷 P1**：数据源运行时缺乏 endpoint SLA、授权复核、供应商重试/速率限制、生产采集错误日志与告警；当前仅支持手动单标的窗口，未建设自动化调度及退避。
- **缺陷 P1**：供应商原始 DataFrame JSON 而非 HTTP byte transcript；哈希防偶然损坏不能防数据库全权限者重算哈希。正式审计需要独立 WORM/对象存储签名、账号分权和可核验采集链路。
- **缺陷 P1**：本轮只有 A 股与场内 ETF 历史日线。贵金属现货/银行纸黄金、期货逐合约与夜盘、国债 YTM/现金流、场外基金 NAV 尚需后续 Provider 适配，且不能自动复用股票 bar。
- **缺陷 P2**：手机侧边栏目前是横向滑动，末尾其他导航项未全部露出。应改成移动抽屉式导航，但不能因此牺牲数据状态显示。
- **模型仍未验证**：任何评分/投资报告不应从 provider release 解禁。R2 首先做历史 PIT 和资产专属 OOS，不是先堆 ML 模型或增加机器人接口。

## 四、结论与下一步
工程上已得到第一条相对可信、**可复核“本次抓取内容”**的数据发布链，解决从来源不明旧库直接拿来评分的问题。成熟化顺序：
1. 正式数据授权与供应商质量监控 + 生产迁移演练；
2. PIT 发布时点、修订、复权、交易日历 / 基金分红与期货展期；
3. 回测/训练模型版本关联 `release_id` 与 OOS 成本报告；
4. 合格候选池 → 人工审阅 → 用户订阅与 WeCom/SMTP outbox（去重、限流、未知结果不自动重试）。
